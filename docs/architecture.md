# Architecture

## Runtime constraints

The deployed code runs in Telegram Serverless V8 isolates. It has:

- ES modules with explicit `.js` relative imports.
- The virtual `sdk` modules: `db`, `api`, `fetch`, `InputFile`, `BotApiError`, `EndpointError`.
- The built-in SQLite database.
- No application filesystem, no npm packages, no Express/Fastify/grammY/Telegraf, no external database.

The project therefore uses only the platform APIs documented in `docs/tgcloud-sdk.md` (generated by the official scaffold) and the module layout from `AGENTS.md`.

## Entry points

| Module | Role |
|---|---|
| `handlers/message.js` | Claims the Telegram update id, then calls `lib/flow/message.js`. |
| `handlers/callback_query.js` | Claims the update id, then calls `lib/flow/callbacks.js`. |
| `endpoints/setup.js` | Explicit command-sync step; callable by CLI, restricted to superadmin over HTTP. |
| `schema.js` | Tables, unique constraints, indexes; applied with `npx tgcloud migrate`. |

Every handler is thin. The platform passes the update payload as the first argument and the full update on `ctx.update`.

## Message flow

```
Telegram update
  -> handlers/message.js (dedup update_id)
  -> lib/flow/message.js
       register/refresh user (one active link on first registration)
       command? -> lib/flow/userCommands.js or lib/admin/commands.js
       admin compose state? -> lib/admin/broadcast.js
       banned/paused checks
       native reply? -> lib/flow/replies.js
       pending deep-link target? -> lib/flow/pending.js
       otherwise -> explain how to start/reply
```

### Deep links

`/start <token>` resolves the active `user_links` row, checks that the owner is not the sender, not banned, and not in a blocking relationship, then writes a one-hour `pending_targets` row. The owner's numeric ID is never sent to the visitor. The next non-command message from the visitor is delivered to the target and revalidates the link is still active.

A visitor can send several messages during the context TTL. Opening another link replaces the context. `/start` with no payload or `/link` clears it.

### Delivery

`lib/services/delivery.js` creates a `conversations` row (one per new message; one shared row per album) and a `messages` row. It stores:

- internal sender and recipient ids;
- parent/root message ids;
- message type, content, sanitized payload, album id;
- source chat/message ids;
- delivery status and Telegram destination ids;
- a random `public_token` used only by the recipient's inline buttons.

It then calls `lib/services/outbound.js`:

- `copyMessage` for a single message;
- `copyMessages` for an album;
- type-specific fallbacks only when Telegram definitively rejects the copy;
- a narrow retry only for 429/5xx responses (never for ambiguous network failures);
- a refusal for `has_protected_content` messages, so protection is not bypassed;
- a re-send path for forwarded messages, so Telegram forward headers are stripped.

A successful copy creates a `message_routes` row **before** marking the message delivered. If a later write fails, the route is still proof that the copy happened, so a duplicate update will not send it again.

### Native reply routing

```
reply_to_message.message_id + current chat id
  -> message_routes (chat_id, telegram_message_id)
  -> internal messages row
  -> verify current user is sender or recipient
  -> destination = the other participant
  -> submitAnonymousMessage(parentMessage = that row)
```

Routes are per delivered Telegram message. Albums create a route per item and one for the control message. This makes multi-level replies and media replies work without a separate wizard. The Reply inline button only displays an instruction; it does not start a conversation flow.

### Albums

Telegram sends each album item as a separate update. Each item is stored as a `pending_album` message with the same `media_group_id` and a shared conversation (`conversations.album_key` is unique). After a short settle delay (`ALBUM_SETTLE_MS`), one handler atomically claims all pending items with:

```sql
UPDATE messages SET delivery_status = 'delivering'
WHERE source_chat_id = ? AND media_group_id = ? AND delivery_status = 'pending_album'
RETURNING *
```

The winner copies the claimed messages with `copyMessages`, creates routes, sends a control message, and confirms once to the sender. Other handlers find nothing to claim. If an item arrives later, it may form a second group; this is a platform timing limitation documented below.

## Database model

All relationships are logical because SQLite foreign keys are disabled by the platform. Integrity comes from unique indexes:

- `users.tg_id`
- `user_links.token`
- one active link per user: partial unique index on `user_id WHERE is_active = 1`
- one conversation per album: `conversations.album_key`
- `messages.public_token`
- `(messages.source_chat_id, messages.source_message_id)`
- `(message_routes.chat_id, message_routes.telegram_message_id)`
- `(blocked_users.blocker_id, blocked_users.blocked_id)`
- `(reports.message_id, reports.reporter_id)`
- `banned_users.user_id`
- `(broadcast_deliveries.broadcast_id, broadcast_deliveries.user_id)`
- `processed_updates.update_id`

`message_attachments` stores file ids and metadata, never bytes. `messages.payload` stores a sanitized type-specific Telegram payload for admin inspection and export.

## Admin architecture

`lib/admin/data.js` owns admin queries and enrichment (loading sender/recipient names in batches). `lib/ui/admin.js` formats HTML, `lib/admin/keyboards.js` owns every inline button, and `lib/admin/callbacks.js` routes them.

Every admin callback re-checks:

1. `callback.from.id === SUPERADMIN_ID`
2. the callback message is in the superadmin's private chat
3. the target record exists

Callback data contains internal ids only in admin contexts. It is never sufficient for authorization.

## Broadcasts

A broadcast is a `broadcasts` row with the admin's source chat/message. Confirmation atomically moves `preview -> sending`. Each batch:

- selects users without a `broadcast_deliveries` row;
- inserts a unique pending delivery row before sending;
- copies the source message;
- records `sent` or `failed`;
- updates counters and shows the next batch button.

At-most-once delivery is intentional: a crash can leave a `pending` row, which is displayed rather than retried and duplicated.

## Exports

`lib/admin/export.js` reads raw SQLite rows with a per-table cap (`EXPORT_ROW_LIMIT`), builds JSON or CSV in memory, wraps bytes in the SDK's `InputFile`, and sends a Telegram document. No filesystem or external storage is used.

## Failure behavior

- Delivery failures are recorded and the sender is told, never falsely confirmed.
- Unsupported/protected types produce a helpful error.
- Update replays are skipped by `processed_updates`.
- Missing/invalid update ids fail closed.
- Authorization errors deny by default.

## Languages (i18n)

`tgcloud/lib/i18n/` holds the localization layer:

- `fa.js` (default, Persian) and `en.js` catalogs with identical key sets; a
  test enforces parity so no locale can silently miss a message.
- `index.js` exposes `t(locale, key, params)`, locale normalization,
  Persian-digit grouping, Jalali (Solar Hijri) date conversion, and byte
  formatting — all pure arithmetic, no ICU dependency.
- Text builders in `lib/ui/`, keyboards in `lib/telegram/keyboards.js` and
  `lib/admin/keyboards.js`, and every flow/service message take the user's
  stored `ui_language` (default `fa`) and resolve copy through `t()`.
- Delivery confirmations use the sender's locale; delivered-media keyboards
  use the recipient's locale; the superadmin report notice uses the platform
  default.
- Telegram command menus are synced per scope and per language (Persian
  fallback + `en`), then verified with `getMyCommands`.
